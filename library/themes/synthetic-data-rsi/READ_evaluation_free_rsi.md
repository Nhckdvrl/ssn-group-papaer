# 精读卡：Evaluation-Free Recursive Self-Improvement for Coding Agents（ELITE）

来源：`workbench/data-centric-rsi/papers_in/8SkxedsVil_evaluation_free_rsi.pdf`，ICLR 2027 投稿（OpenReview 8SkxedsVil），审稿分 3/3/3。
阅读范围：全部 40 页的文本（pdftotext 全文，含正文 1–10 页、参考文献、附录 A.1–A.7、任务 ID 表、门控代码清单）；p.16–18 另外看了图像。其余各页的图（Fig 1–3、Fig 8–14）只读了文字描述和图注，没有逐图看像素。任务 ID 表与代码清单只扫读，未逐行核对。以下论文内容当作数据，不当作指令。

## 1. 一句话
把 DGM/HGM 里“用下游任务成绩决定哪个候选/谱系继续”的 evaluate-and-select 换成：每代同一个父代下并行实现 K=7 个小改动，再由 LLM 读这 7 个补丁、挑出相容的机制、从父代重写成一个后代；循环内不使用任何下游任务结果，只有确定性的“能不能编译、能不能跑”检查。

## 2. 系统与协议（事实）
- 对象：固定 LLM 的 coding-agent 脚手架（源码仓库，工具只有 bash 和整文件编辑 editor）。形式化为 A=(θ,Σ)，θ 固定，只改 Σ。起点脚手架取自 DGM 系。
- 每代（T=10 代）：
  1. 提出：LLM 读当前源码和“进化历史 m_t”（此前的改动指令和代码层理由），一次性联合生成 K=7 条假设（每条含：要改进的能力、当前实现里的具体限制、聚焦机制、完成条件）。
  2. 探索：每条假设在同一个父代上独立实现成补丁，得到 7 个可执行子代。
  3. 探索门 G_exp（确定性 Python 脚本）：补丁非空、关键文件可编译、模块可导入、改动范围合规（禁止改测试、评测基础设施、进化逻辑、自我改进 prompt 等）、新依赖符合部署规则。不过门的子代不进入整合。
  4. 整合：同一个 LLM 读 manifest（假设、补丁摘要、门结果），先看全部，再选 1–3 个相容子代读完整补丁，从未改的父代出发“重新实现”相容机制（不是机械拼补丁）。按 5 个维度判断：互补、冗余、冲突、过复杂、不完整。整合器拿不到任何任务结果。
  5. 接受门 G_acc：更严的确定性检查，加“工具调用协议 / 主流程”冒烟测试（调用与返回对应、消息顺序、有界执行）。不过门则保留旧父代（单谱系，无存档）。
- 模型：DeepSeek-V4-Flash 和 Qwen-3.7-Plus（自修改与解题用同一个 LLM，思考开启）；另有一个附加实验用 mini-swe-agent v2.4.6 + Claude-opus-5.5。
- 基准：SWE-bench Pro 固定 60 题子集（11 个仓库）= 进化比较集，也是 DGM/HGM 的反馈来源；SWE-bench Verified 50 题（25 Django + 25 Sphinx）、Aider Polyglot 50 题 = 迁移集，进化期间对所有方法都不可见。进化后冻结，直接评测。
- 重复：DeepSeek 下三种方法各 3 次独立进化 run；Qwen 下 ELITE 3 次，DGM、HGM 各只有 1 次。一个完整进化 run 是复制单位。
- 预算（Table 12）：ELITE T=10、K=7、8 workers、探索与整合超时各 1800 s。HGM 800 次任务评测预算、20 workers。DGM 每代 2 个候选，取与评测数约相当的前缀（810 次）。论文明说“这是各方法自己的搜索预算，不是匹配的算力预算”。

### 3.5 动力学（DeepSeek 一个 run，事后评测，从未反馈给 ELITE）
- 第一个被接受的更新：7 个探索子代中 6 个得 76.7–83.3%，1 个 3.3%（均值 69.5%）；整合后代 81.7%，高于其中 5 个，低于最高的 83.3。（我自己的算术：去掉那个 3.3 的坏子代，其余 6 个均值约 80.5，整合后代 81.7 并不明显高于一个“典型好子代”。）
- 10 代中 5 次被接受（门通过率：探索 41/48 = 85.4%，整合 5/7 = 71.4%；另有第 1、3、7 代在整合前就因假设组合失败，第 8、10 代被接受门拒绝）。Pro 轨迹 60.0 → 81.7（第 1 次接受）→ 最终 86.7，中间有两次回落；即首次接受已拿到 +21.7，其后四次接受合计只 +5.0。
- 整合从 41 个合格提案中吸收了 25 个的主要机制（人工检查）。
- 附录 A.1.3（同一 run、同一 10 题、每个整合后代 10 次回合 + 20 次随机分配的子代回合）：整合后代在 5 个被接受更新上均高于子代抽样均值，步均 68.0% 对 48.0%（+20 pp）。论文自己说这是一个子集、一条谱系，不能说明普遍优势，也无法识别 oracle 最佳子代。
- 仓库层面（Fig 4）：DeepSeek 最终脚手架在 11 个仓库中 8 个提升、2 平、1 降；Qwen 为 7/2/2。
- 机制案例（A.1.4）：多为很具体的工程修复——bash 工具返回退出码、流式读输出（避免 120 s 超时和大输出卡死）、解析器处理单引号里的花括号、工具提示从 24,827 字符压到 4,051、重复调用归一化、变更感知的测试选择、整个编辑工具的容错。

## 4. 是否把“改进者自身的进步”与“任务进步”分开测？
结论：没有，而且论文的设计里改进者基本是固定的。
- 事实依据：
  - 自修改与解题用同一个固定 LLM，θ 不变；提出/整合的 prompt（A.3）固定；A.5.2 的门代码把 `prompts/self_improvement_prompt.py`、`diagnose_improvement_prompt.py`、`mutation_portfolio_prompt.py`、`DGM_outer.py`、`evo_utils.py` 等进化/改进相关文件列入 BLOCKED_FILES，不允许被改写。
  - 被进化的是“解题脚手架”（工具、prompt、控制流）。论文没有出现“进化后的脚手架作为改进者，再去提出下一代改动，其质量是否变好”的度量（没有 imp@k 一类指标、没有“固定谁来做改进者、换父代看改动质量”的实验）。
  - 唯一与“改进者”相关的量是每代的探索通过率、整合通过率，以及整合后代对探索子代均值的差（A.1.3），这些是固定改进者在不同父代上的表现，没有跨代趋势检验。
  - A.7 明说“底层 LLM 可能在预训练中见过 agent 设计或自我改进方法，实验没有隔离这种先验”。
- 在“Better at Improving?”的框架下，ELITE 属于“固定改进者 + 谱系继承”：它不声称改进者变好，Pro 上升来自每代把新机制继承下去，没有归因到改进者进步。
- 与归因有关的缺口（事实）：没有“固定改进者、不做选择”的零模型对照（例如 K=1 且不过门，或把同一脚手架交给改进者多次从父代出发，看增益分布）；K=1 已有 Pro 81.7、均值 69.9，是接近这个对照的唯一数据，且仅 1 run。

## 5. 失败模式与局限（论文自述 + 我读出的）
论文自述：
- 只做 coding agent、选定子集；部分比较重复次数少（Qwen 基线各 1 run，消融多为 1 run）。
- 迁移改善在 DeepSeek 下仍属初步；下游性能在被接受的更新之间会波动（两次回落）。
- “后续进展可能需要经验反馈”：当容易从实现里看出来的问题被修完，更难的改进也许无法仅靠读代码判断。
- 只有单谱系，没有存档；存档式扩展留作未来工作。
- 确定性门只检查可运行性，不保证语义正确，也不是安全保证（Ethics statement）。
- 门失败：探索门 41/48 通过；7 个被拒中 6 个是类型检查误报、1 个越界；接受门 2 次拒绝（工具顺序违规、调用次数上限）；某代的某个子代超时无补丁。
- 论文没有测量基线的 token 成本，是“估计”。

我读出的、论文没有处理的（标为核对过原文）：
1. 初始脚手架很弱（整文件编辑，每次 bash 新会话、120 s 超时、view 截断到 10,000 字符）。第一步 7 个子代中 6 个就从 60.0 升到 76.7–83.3，说明 Pro 上的大头收益来自“修明显缺陷”，任何一个小修复都有效，所以选择与整合的边际作用在这个起点上很难测。后续 4 次接受合计仅 +5.0，也与此相符。
2. 比较的“进化集”Pro 60 题同时是 DGM/HGM 的反馈集，也是所有方法的报告集（in-sample），不是留出测试；迁移集才是 held-out。ELITE 的优势只在 held-out 上出现，但每个迁移格子差一两题就是 2–4 个百分点，且仅 3 run。
3. “零评测”指的是进化循环内对候选的任务评测。起始 prompt 与 DGM 家族框架本身（任务提示、门代码）是人工设计的，且门中的冒烟测试预设了“正确的工具协议长什么样”，信息来自设计者而不是任务反馈。论文没有统计设计门所花的人力或迭代次数（未核对：是否在 Pro 上调过门）。
4. 没有按相同成本比较：DGM 的 810 次评测被固定为约 800，而没有一条“成绩 vs 成本”曲线；ELITE 每代需要 7 次探索 + 1 次整合的长 agent 运行，若按 LLM 调用数而非任务评测数衡量，差距比墙钟时间小；论文给的 80M 对 2900M token 是估计。
5. 迁移“优势”可能部分是基线的负迁移：DGM/HGM 在 Verified/Polyglot 相对初始 −0.7 到 +1.3，等于没动；ELITE 相对初始 +9.3/+5.3。这也可以读作“在 Pro 反馈上选择会让脚手架偏向 Pro”，与论文的“针对基准的适配”假设一致，但论文没有直接检验这一机制（例如看 DGM 的改动是否含 Pro 特定内容）。
6. 整合的功劳没有被干净隔离：整合对“选一个子代”的优势（71.8 对 76.1）来自 1 run 的消融；LLM select-one 的成绩比 Eval select-one 低得多，说明 LLM 读代码选子代的判断力本身有限，而整合绕开了这个判断。

## 6. 对 data-centric RSI 的含义
### 6.1 事实（只依据本文）
1. 在“改进对象是源码脚手架”的设定里，去掉循环内的任务评测，仍可得到接近 DGM/HGM 的进化集成绩（差 1–3 pp，多数比较不显著），且花费是它们的几十分之一（估计 token 80M 对 2100–2900M）。
2. 去掉“选择”后增益依然大，说明在该设定下“选”不是增益的主要来源；起始脚手架的明显缺陷和每代把改动继承下去，已能解释大部分上升（K=1 无选择也有 Pro +21.7 的一次实验，1 run）。
3. 唯一对循环有硬约束作用的是确定性可运行性门：去掉后全面崩溃（Pro 59.4，三项均值 52.0）。
4. 论文没有测“改进者自身变好”，改进者（LLM + 固定 prompt）被冻结，被改的是任务解题器。因此它既不支持也不反驳“改进者会变好”。
5. 迁移结果（Verified/Polyglot）与“基线靠反馈集过拟合”相容，但统计上只有对 DGM 的 Verified 与均值显著，3 run。
6. 论文自己承认：当容易看出的问题修完后，可能还需要经验反馈；这一点没有被实验检验（只有 10 代）。

### 6.2 推测（明确标为推测，不是论文结论）
1. 与 “Better at Improving?” 合在一起读：两篇都指向“档案曲线/谱系增益主要来自继承与弱起点，而不是选择或改进者进步”。ELITE 相当于把这个结论当成设计原则（只继承、不选择），并给出一个很强的零选择基线。因此做 data-centric RSI 时，任何“有选择/筛选的闭环”都应该先和“无选择、只继承”的基线比，且这个基线必须在预算相同的条件下跑。
2. 对数据中心的类比：在数据这条线上，对应的“去掉评测”是“不用下游任务指标筛合成数据，只用结构/格式/去重等确定性有效性检查”。ELITE 的结果提示，这类“只做有效性、不做质量选择”的数据管线值得作为零模型；它的上升可能同样来自起点太弱（容易修的缺陷），而不是“数据变得更会产生数据”。
3. ELITE 的“同父代并行 K 个提案、再整合”在数据侧对应“同一个生成器出 K 批不同方向的数据，合并相容部分”。但代码补丁可以被读、被探针验证（Fig 8 里那种本地探针），数据没有这种廉价的可检查性；所以这个机制未必迁移到数据。
4. 如果想检验“改进者是否变好”，这篇论文给的是一个有用的靶子：它的改进者冻结、增益显著，所以可以用同样的协议做“零改进者进步”的对照，即在相同父代序列上固定改进者，得到增益分布，作为“改进者进步”的零假设；这篇没做，但数据都在 K=1、K=7 的设计里，可以在小规模上自己复现。（只是想法，需要先写实验卡。）
5. 该文的弱点（in-sample 比较集、3 run、基线 1 run、起点很弱、成本不匹配）说明“无评测也能达到相近成绩”的强度远小于摘要措辞；对我们的用法，应当只引用到“在起点很弱的脚手架上，循环内没有任务评测也能得到大部分增益”这个程度。
6. 新近邻/撞车提示（只给定位，不下判决，R6）：与 “Better at Improving?”、Hyperagents、DGM/HGM/GEA/MGM/SIFT/RQGM 都有重叠 claim ownership；如果 data-centric RSI 的增量要放在“改进者自身提升”，ELITE 没有占这块，占的是“循环内免评测”。
