# E232：分辨力还是门槛？用判定处的 Yes / No 概率算 AUC，并覆盖 OLMo-3 全部后训练阶段（2026-11-25）

- **状态：** PLANNED
- **类型：** PILOT（[提案](../TOPIC_PROPOSAL.md) 第 8 节检验 1；不推进主张）
- **对应：** Q3（分辨力 vs 门槛）、Q2（各阶段）。前置 E230、E231。用户 11-25：“跑，多卡并行”。

## 问题

E231 里，中性检查语下三种放法的误报率都接近 0（地板），所以“接着写时分辨力下降”和“接着写时否定门槛更高”从比例上分不开。本卡改用不依赖门槛的分级读数：在判定处读模型给“incorrect”与“correct”的对数概率之差 m，按题算错答案与正确答案之间的 AUC。
- **AUC：** 只看 m 能否把错答案排在正确答案前面，与门槛无关。
- **m 的平均值：** 看整体偏向“correct”还是“incorrect”，即门槛。

**锁定验算文字的读数（关键）：** 在三种放法里，检查语之后都接上**同一段**验算文字，再读判定。验算文字给出正确结果：错答案版里它与给出的答案矛盾，正确答案版里它与给出的答案一致。于是三种放法之间唯一的差别，只剩这段验算接在“自己正在写的话”后面，还是接在别人的话后面。若 C 的 AUC 仍低于 O → 验算都做对了，结论仍被拉偏：分辨力受损；若 AUC 相同、只是 m 整体偏向 “correct” → 门槛移动。

## 设置

- **模型（OLMo-3-7B 同一 base 的 8 个阶段）：** base（`Olmo-3-1025-7B`）；Instruct 线 SFT / DPO / 最终（RLVR）；Think 线 SFT / DPO / 最终（RLVR）；RL-Zero-Mix（从 base 直接做 RL，不经 SFT）。
- **数据：** SCLI5 286 题、GSM8K-SC 前 300 题，各有错答案版（Tsui 注入的错误）与正确答案版（E231 的构造）。
- **放法：** C / S / O（同 E230）。**格式：** F1 纯文本（全部模型）；F2 chat 模板（后训练模型）。
- **检查语：** V（“Let me check whether this answer is correct.”）；W′（“Wait, let me check whether this answer is correct.”，看 “Wait” 改变的是 AUC 还是 m 的平均值）。
- **两种读数：**
  - **直接判定：** 检查语后接 “ Verdict (correct or incorrect):”，读下一个 token。
  - **锁定验算：** 检查语后接 “ Recomputing: {验算文字} Verdict (correct or incorrect):”。验算文字：SCLI5 按题型从题面生成（如 “14 is smaller than 19, so the smaller one is 14.”）；GSM8K 用数据集的标准解答（去掉计算标注与 `####` 行）。
- **读数位置：** m = log P(“ incorrect”) − log P(“ correct”)（跑前核对两者在分词器里各是一个 token；若不是，用首 token 并在结果里写明）。只做前向传播，不生成。
- **命令：** `scripts/e232_verdict_auc.py`；fvcrc20 GPU1–3。

## 读数与判定

- 每个模型 × 格式 × 数据 × 检查语 × 读数 × 放法：AUC（错 vs 对，Mann–Whitney）；m 的平均值。
- **主比较：** 锁定验算读数下，AUC_O − AUC_C 与 AUC_S − AUC_C（按题 bootstrap，2000 次）；m 平均值的 C − O。
- **全部题目都用**（新阶段模型没有 E229 的知识门）；base / SFT / Instruct 另报知识门后的结果作敏感性分析。

## 阳性对照与噪声

- **阳性对照：** O 条件、锁定验算读数下 AUC 应明显高于 0.5（验算给出了答案，读数若有效应接近 1）。O 的 AUC < 0.7 时，说明读数位置或 token 不对，不解释。
- **噪声：** 每版约 286 / 300 题，AUC 的标准误约 0.02–0.03。AUC 之差 < 0.05 不作为“有差别”。

## 混杂审计

- 验算文字与错误文字风格不同（GSM8K 用数据集解答）：三种放法用同一段，条件间比较不受影响。
- 锁定验算对 base 是不自然的文本（“Recomputing:” 之后给出与前文矛盾的结果）：同样在三种放法里一致。
- Think 模型的 chat 模板可能自动插入思考标记：跑前打印 F2 的 prompt 核对；若模板强制插入，按模板原样，并在结果里写明。

## 结果（跑完后填写；不改上面的内容，修改需注明日期）

**实际算力与经过：**
- 前向打分 8 个模型，每个 3–6 分钟，合计约 0.8 GPU·时，在 fvcrc20 上。5 个阶段模型从 HF 下载约 1 小时（限速约 2.4 MB/s / 流）。
- `Olmo-3-7B-RL-Zero-Mix` 的配置写的是 `olmo2-retrofit`，transformers 4.57 不认识。核对后其余配置项与权重名（355 个）都与 base 完全相同，于是用只改了架构名（`Olmo3ForCausalLM`）的配置副本加载，权重不动（`models/olmo3_rlzero_patched`，符号链接）。
- 跑前核对：“ incorrect” / “ correct” 各为单个 token（15465 / 4495）。

**阳性对照：** O 条件、锁定验算读数下 AUC 全部 ≥ 0.94 → 读数有效。

**主读数：锁定验算，中性检查语 V（AUC 与 m 的平均值；m > 0 偏向 “incorrect”）**

（后训练模型为 F2；所有阶段 AUC_O − AUC_C 的区间都在 ±0.012 以内。）

**按决策表执行：**
- 落在“**门槛移动**”一行：所有 8 个阶段，锁定验算后三种放法的 AUC 都在 0.96–1.00、彼此之差 < 0.05；而 m 在接着写（C）时一致地更偏向 “correct”（16 格里 C 的 m 都低于 O，差 0.15–2.6；SFT 的 GSM8K 与 RL-Zero 两格差距很小）。
- **含义：** 只要验算写在眼前，模型在接着写时仍能把对错完全分开；“看不见”来自自己正在写的话把判定往“对”那边拉，不是分辨力坏了。这修正了 E231 的初步判断（E231 因误报率在地板上暂记为“敏感度下降”）。
- **各阶段：** Think 线（尤其 Think-DPO）与 RL-Zero 把 m 整体推向 “incorrect”（更爱否定），但 C 低于 O 的顺序仍在（RL-Zero 的 GSM8K 例外，几乎无差）。推理训练移动的是整体门槛，不是消除了“偏向自己”。
- **W′（“Wait, let me check…”）相对 V：** AUC 基本不变或略降，m 整体上移（偏向否定）。“Wait” 主要移动门槛，与 E231 的高误报一致。

**直接判定（不给验算）：** AUC 在 0.47–0.95，O − C 之差在 −0.06 到 +0.12 之间，多数 < 0.05；m 的 C − O 差很大（如 Instruct SCLI5：−7.04 vs −1.73）。不给验算时，同样主要是门槛差。

**保留：**
- 锁定验算的 AUC 全部接近天花板。“分辨力没坏”的结论限定在“验算已经写在上下文里”的条件下；没有验算时，AUC 本身就不高，无法判断天花板以下的细微差别。
- RL-Zero 用了改名后的配置加载，结构与权重核对一致，但不是官方加载方式。
- POST-HOC：RL-Zero 在 W′ + GSM8K 锁定验算下 AUC C 0.74 vs O 0.94，是全表唯一明显的分辨力差，原因未查。
