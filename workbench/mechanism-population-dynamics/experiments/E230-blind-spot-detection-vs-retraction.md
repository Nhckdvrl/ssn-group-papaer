# E230：接着写时没纠正，是看不见错，还是不肯开口检查？（2026-11-25）

- **状态：** PLANNED
- **类型：** PILOT（候选 D 的第二刀；不推进主张；锁题由人决定，R2）
- **对应：** [TOPIC_SEARCH.md](../TOPIC_SEARCH.md) 候选 D；前置 [E229](E229-self-correction-blind-spot-origin.md)。用户 11-25 选“先拆开看不见错与改口代价”。

## 问题（给外人看的版本）

E229 里，模型在“接着写”自己刚写错的那段话时几乎从不纠正（base 0.01–0.03），新开一轮或回复别人时却能纠正。但这两种情况的任务不一样：新开一轮时模型可以直接重答一遍；接着写时，要答对就得先主动停下来、推翻自己刚写的句子。所以 E229 分不清两种解释：
- **看不见：** 模型在接着写时，确实没有意识到前面错了（自己的文字让它的判断偏向“前面是对的”）。
- **不开口：** 模型其实“看得见”，只是不会在一段话中途主动停下来检查、改口。

**一刀切开的对照：** 在三种条件里，都在模型要写的文字开头放上**同一句检查语**，让它们都必须先检查前面的答案，再往下写。这样三种条件的“改口代价”就拉平了：
- 若接着写的纠正率追上另两种：盲点是“不开口”，不是“看不见”。
- 若仍明显落后：即使被要求检查，自己正在写的这段文字仍让它看不出错，是真正的“看不见”。

**近邻：** Tsui 只在 internal 条件后面加 “Wait”，拿去和不加 “Wait” 的 external 比（盲点缩小 89.3%），**没有在三种条件里放同一句话**，所以同样分不清这两种解释。Zhang 2023（hallucination snowballing）发现模型单独被问时能认出自己先前的错误陈述，但那是换了上下文问，不是在“接着写”的位置上。Essential AI 2504.04022 在 base checkpoint 上加 “Wait,” 看反思，但没有“同一错误、只换归属 / 位置”的对照。

## 设置

- **模型、数据、知识门：** 与 E229 完全相同（OLMo-3-7B base / Instruct-SFT / Instruct；SCLI5 286 题 + GSM8K-SC 前 300 题；知识门直接复用 E229 的 clean 结果，同模型同 greedy）。
- **检查语（加在模型要写的文字最前面，三种条件逐字相同）：**
  - **V（中性）：** “Let me check whether this answer is correct.”
  - **W（Tsui 的标记）：** “Wait,”（偏向改口，作为对照，不作主读数）
- **三种条件 × 两种格式：** 同 E229。检查语的位置：
  - C：错误句后接一个空格和检查语，模型接着写（同一段话里）。
  - S：B 的新一段 / 新的 assistant 消息以检查语开头。
  - O：B 回复 / assistant 回复以检查语开头。
- **解码与截断：** 同 E229（greedy；SCLI5 160 token，GSM8K 384 token；在下一个说话人标记 / EOT 处截断）。
- **命令：** `scripts/e230_check_frame.py`（复用 `e229_blind_spot.py` 的数据与格式函数）。
- **跑前发现的格式差异（11-25，如实记）：** OLMo-3 的 chat 模板把“最后一条 assistant 消息”以 `<|endoftext|>` 结尾，把“非最后一条”以 `<|im_end|>` 结尾。E229 的 S 里，错误那条是最后一条（后接生成提示），因此以 `<|endoftext|>` 结尾；本卡的 S 里后面还有一条以检查语开头的 assistant 消息，错误那条以 `<|im_end|>` 结尾，这是模板对多轮对话的正常渲染。本卡内部三种条件之间的比较不受影响；与 E229 的 S 比绝对值时需注意。

## 读数

- **主读数：** V 下的纠正率（最终答案正确，同 E229 的评判模型与提示词；评判时把检查语和续写拼在一起给评判）。主比较 V 下的 O − C 和 S − C。
- **辅读数：** “是否明确指出前面的答案错了”（同一评判模型，另一个固定提示词），看纠正是“重答”还是“指出错误再改”。
- **参照：** E229 中不加检查语的 C / S / O。

## 阳性对照与噪声

- **阳性对照：** 检查语应提高 C 的纠正率（Tsui：“Wait” 大幅降低盲点）。最终 Instruct 的 C 在 W 下若不升，说明插入方式有问题，先查格式。
- **噪声：** 同 E229，n ≈ 190–280 时 95% 区间约 ±0.06；差值 < 0.15 不作为“有差别”。
- **评判校验：** 随机抽 40 条人工复核两个评判问题；低于 90% 时对分歧类别人工复核。

## 混杂审计

- **检查语改变了 S / O 的自然回复方式：** O 可能因此下降（本来直接给答案，现在要先评估）。主比较是加了检查语之后三种条件之间的差，不是和 E229 比绝对值。
- **“Let me check” 本身暗示可能有错：** 三种条件里暗示程度相同，不影响条件间的比较；但绝对值会被抬高。
- **base 在 F1 里可能不理会检查语：** 按条件报告“续写里没有任何检查内容”的比例。
- **单一家族、S 的格式不自然：** 同 E229。

## 结果（跑完后填写；不改上面的内容，修改需注明日期）

**读数的偏离（如实记，11-25）：** 按卡做评判校验时发现两个原评判都不能用：
- “是否指出前面错了”会把检查语本身当成指出错误（SFT 只写了检查语、什么都没续写，也判 Yes）。
- “最终答案对不对”把 “8 is smaller than 12. Yes, the answer is correct.” 这类“事实写对、结论却认可错答案”的输出判成答对，而这正是本卡最关键的一类。
- 因此改用**三选一结论评判**（只看模型自己写的部分，不给评判正确答案）：A 认可 / 保留给出的答案，B 否定 / 改成别的答案，C 没下结论；外加一条确定性规则：有明确认可短语且没有任何否定短语时记 A。
- 校验：在 60 条（用来调提示词）上 57/60 一致；在另抽的 40 条新样本上 38/40 一致（只用评判、不加规则：36/40）。下面主读数用“评判 + 规则”，只用评判的数字在 `results/e230/summary_verdict_judgeonly.json`，方向全部相同。原评判的数字保留在 `results/e230/summary.json`，不作解释。

**按决策表执行：**
- 阳性对照通过：检查语让 C 明显上升（例：base SCLI5 从 E229 的 0.03 到 V 0.21、W 0.97）。
- 插入方式有效（只有 SFT 的 chat + V + SCLI5 一格例外，按卡不解释）。
- 主读数落在**第二行**：base 与最终 Instruct（chat）都是 O − C ≥ 0.15、区间不含 0 → **即使被要求检查，模型对自己正在写的这段话仍更少看出错。** 典型输出（base）：“14 is smaller than 19. Yes, the answer is correct.” 事实算对了，结论仍认可自己刚写的 19。这一点不能用“改口代价”解释，因为三种条件都已被要求先检查。
- 差距随训练阶段缩小：C 里“认可错答案”的比例 base 0.79–0.90 → SFT 0.52–0.62 → Instruct 0.28–0.29（chat）。

**解读上的保留（重要，未核对）：**
1. **缺“给出的答案是对的”对照。** 所有题里给出的答案都是错的，所以“否定率”混合了两件事：看出错（敏感度）和倾向于否定（标准）。O 里的高否定率可能部分来自“对别人的答案一律更挑剔”，C 里的低否定率可能部分来自“对自己的答案一律更认可”。“Wait,” 下几乎 100% 否定，很可能就是标准被推到了极端，而不是看得更清楚。要分开这两者，需要在同样的位置放上**正确答案**，看误报率（信号检测的做法）。这是本卡设计的漏洞，应在下一张卡补上。
2. F1 里 Instruct 的 SCLI5 O 有 26% 没下结论（被续写成别的内容），这一格的 O − C 不可靠。
3. 只有 OLMo-3 一个家族；评判仍有约 5% 误差，且误差方向偏向把“认可”判成“否定”（会缩小 O − C）。
