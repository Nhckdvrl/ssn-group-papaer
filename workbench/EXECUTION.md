# 执行协议 — 把题做出来

**版本：v4.1（2026-10-01）。** 配套：[`README.md`](README.md)（驻留与容量）、[`IDEA_EXPLORATION.md`](IDEA_EXPLORATION.md)（idea 从哪来、怎么筛）、[`../templates/`](../templates/README.md)（卡片模板）、[`../tools/process/`](../tools/process/README.md)（生成与检查工具）。

## 0. 一句话

> **每一次运行都要推动一条主张或回答一条痛点；主张按证据等级往上爬；每次人审只问一件事——哪条主张升了级、哪条降了级、为什么。**

v3 只规定了“去哪里驻留”，没有规定“驻留时怎么干”。结果是好的线也会在执行中漂移：视频线的 E29 真人回放，选窗方式把“接缝位置”和“按键时长”绑在一起，直到第二轮校对才发现，主结论“55% vs 27%”因此作废。多数结论停在 n=3–5、单种子。本协议把这类问题变成流程里的固定检查，而不是靠运气在校对时撞见。

---

## 1. 三本账

| 账 | 文件 | 记什么 | 谁写 |
|---|---|---|---|
| 痛点日志 | `PAIN_LOG.md`（P##） | 跑的过程中坏掉的、不稳定的、慢的、指标之间不一致的、意外地好的 | 执行者随手追加 |
| 实验卡 | `experiments/E##-<slug>.md` | 一次实验的问题、设置、读数、对照、决策表、结果 | 跑之前写上半部分，跑完写结果 |
| 主张账本 | `CLAIMS.md`（C##） | 每条可证伪的主张、证据等级、证据来源、已知威胁、校对状态 | 结果出来后更新；降级也要记 |

另有 `ideas/I##-<slug>.md`（idea 卡，见 `IDEA_EXPLORATION.md`）和 `logs/YYYY-MM-DD.md`（每次会话一条：做了什么 → 结果 → 哪条主张变了 → 下一步 → 需要人决定的事）。

生成：`python3 tools/process/new.py experiment <workbench> <slug>`、`... idea <workbench> <slug>`。检查：`python3 tools/process/check.py`。

---

## 2. 实验卡：跑之前写

必须在运行前写完的字段（模板 `templates/experiment_card.md`）：
1. **对应**：主张 C## / idea I## / 痛点 P##，至少一个。说不出对应什么的运行，只能算 EXPLORE。
2. **读数**：指标定义；明确说明读数是否与被测变量解耦（选窗、采样、归一化、自校准）。
3. **阳性对照**：在已知有效应的地方，工具能测到吗？（L29：比较训练阶段之前，先在参考点证明干预有杠杆。）
4. **噪声地板 + 最小有意义效应（MIE）**：重复测量 / 种子方差是多少？多大效应才会改变决策或科学解释？L19 的教训是先比较 effect 与 measurement resolution，不是把 `2×noise` 变成通用硬阈值。
5. **决策表**：结果 A → 做什么；结果 B → 做什么；不确定 → 加多少 n。决策表写不出来，说明这个实验还不值得跑。
6. **算力预算**：GPU·时估计。

跑完后只追加“结果”部分；上半部分如需修改，注明日期与原因。事后才想到的分析标 **POST-HOC**，不能单独支撑主张升级。

**探索预算**：D1/D2 的 baseline reproduction、harness 建设和领域标准 measurement **不计入 EXPLORE 配额**；它们本来就是驻留。只有 strong baseline 已跑通、至少出现一个真实 pain/measurement signal 以后，才开始统计 EXPLORE。此后不对应任何主张 / idea / 痛点的 EXPLORE 运行，在两次人审之间默认不超过该 workbench GPU·时的 30%。30% 是漂移 heuristic，不是为了逼 agent 随便挂 I##；若人认为更高探索比例合理，可以在 review 里显式批准。

## 3. 证据等级

| 等级 | 含义 | 最低要求 |
|---|---|---|
| **L0 个例** | 看到了 | 1 个例子 / 1 个场景 |
| **L1 pilot** | 可能是真的 | 阳性对照通过；效应大于噪声地板估计；1 个模型、小 n |
| **L2 重复** | 在一个设定里是真的 | ≥3 个种子或每条件 ≥20 个样本/场景；报置信区间；§4 混杂审计完成 |
| **L3 泛化** | 不只是一个模型的事 | ≥2 个模型家族或尺寸，且 ≥2 个任务 / benchmark（系统级主张：≥3 个独立系统） |
| **L4 机制 / 因果** | 知道为什么 | 干预（消融、patching、网格平移、反事实替换）按预测改变结果；主要替代解释被排除 |
| **L5 论文就绪** | 审稿人挑不出硬伤 | 强基线 + 等算力对照 + 关键消融 + 独立校对（§5） |

这些等级是**默认 evidence targets，不是自动判决器**。不同 claim（系统、理论、测量、机制）的合适证据规模可能不同；任何偏离需在人审中说明为什么仍足以支撑该 claim。

各阶段的默认门槛：

| 阶段 | 要求 |
|---|---|
| 驻留交付（D1–D6，形态卡初稿） | 每个预期贡献至少有一条 L1 主张，或明确标 ❌ |
| 进入 candidate | 主旨主张通常 ≥ L3；所有 manuscript-critical contributions 达到与其措辞匹配的证据（通常 ≥ L2）；凡写成“机制/因果”的主张通常 ≥ L4；全部通过校对。不要为了凑固定数量的贡献而 padding。 |
| 投稿 | 摘要里的每条主张 ≥ L3 且完成 L5 清单；达不到的写成局限或初步观察 |

**主张的适用范围要写进主张本身。** 例：视频线“流式交互中每次起步都丢第一个潜变量”只对位姿条件模型成立（MG2 不同），“触发条件是块与上下文的位姿跳变”目前只在 WorldPlay 上成立——主张写成通用结论之前必须在另一个系统上复现。

## 4. 混杂审计清单（主张升到 L2 之前逐项过）

每项写“无关 / 已控制 / 未控制（原因）”。例子全部来自本仓库。

| # | 检查 | 问法 | 本仓库的例子 |
|---|---|---|---|
| 1 | 噪声地板 | 效应是否明显大于重复测量的波动？ | L19 |
| 2 | 工具有效性 | 在已知有效应处能测到吗？ | L29 |
| 3 | 选窗 / 采样耦合 | 样本怎么选的？选法会不会和被测变量相关？ | 视频 E29：滑窗规则把按键时长变成了接缝位置 |
| 4 | 自校准读数 | 读数的标定是否在各条件间共享？ | 视频 E29：每个条件用自己的增益换算角度，修复后 +36% 的过度转动被藏住 |
| 5 | 提示词默认值 | 一句指令能否恢复？测到的是能力还是默认策略？ | 实时线：abstention 1/39 → 一句指令 39/40 |
| 6 | 输入一致性 | 纵向比较时，每个 checkpoint 的输入字节是否一致？ | S03：tokenizer 漂移 |
| 7 | 幸存种子 | 是否只报了“好”的种子？ | L45 |
| 8 | 算力匹配 | 与等调用 / 等 token / 等训练算力的强基线比过吗？ | 多智能体：辩论 vs self-consistency |
| 9 | 数据污染 / 集合重叠 | 训练、pilot、测试是否分开？benchmark 是否在预训练里？ | — |
| 10 | 多重比较 / 事后切片 | 看了多少切片才找到这个？是否标了 POST-HOC？ | — |
| 11 | 饱和 / 地板效应 | 读数是否贴着上下限？ | 视频 E26：单步 x₀ 不灵敏，作废 |
| 12 | 系统特有 vs 一般 | 结论在哪些系统上验证过？主张的措辞有没有超出范围？ | 视频：机制在 minWM 与 WorldPlay 上不一致 |

## 5. 校对（独立复算）

主张升到 L3 以上、或写进论文形态卡的“摘要主张”之前，由**另一个人或另一个 agent 会话**做一次校对：
- 从原始结果文件（`results/`）和脚本重算关键数字，不看作者的汇总表；
- 读一遍产生样本的脚本（选窗、过滤、归一化），对照 §4；
- 结果写进 `CLAIMS.md` 的“校对”列与 README 的“校对备注”。

视频线的“校对备注·第二轮”就是范例：它发现了选窗伪影、自校准读数和机制的跨系统不一致，并把受影响的主张降级。**这一步要常规化，而不是等到评估文档时才做。**

---

## 6. 算力与排程（单节点 4×A100 80GB 或 4×RTX PRO 6000 96GB，两台不互通）

- **不排时间表，只排优先级**：① 决定性 pilot 与推进主张的实验 → ② 复现与覆盖面 → ③ EXPLORE（≤30%）。agent 执行很快，瓶颈是算力和决策质量，不是日程。
- 长训练与短诊断交错排队，保持反馈回路快：长训练在跑时，用空闲卡做推理评测与分析。
- 每张实验卡记录估计与实际 GPU·时；每次人审汇总。
- 投稿前保留一部分算力给重跑与审稿人可能要的对照。
- `env.sh` 固定版本（框架、CUDA、flash-attn、模型 revision）；checkpoint 与大文件的路径写进 README“资产位置”。
- 不假设多节点；需要多节点的实验在形态卡里写成风险，而不是计划。

---

## 7. 截稿日：外部约束，不是计划

不做按周倒排。截稿日只用来回答一个问题：**到截稿时，主张够不够投？**
- 够（摘要里每条主张 ≥ L3，且完成 L5 清单与模拟审稿）→ 投最近的会；
- 不够 → 投下一个会议，线继续推进，**不关闭**（`README.md` §6）；
- 顺序固定、不排日期：主张到候选门槛 → 候选包 → 写作 → 模拟审稿 → 修复 → 独立校对 → 投稿（`../candidates/README.md`）。

---

## 8. 漂移检测

漂移按“做了多少、推进了多少”来判断，不按日历。出现任一信号就触发一次人审，只讨论它：

| 信号 | 例 |
|---|---|
| 连续 5 张完成的实验卡没有让任何主张变化 | 在加覆盖面，但没有推进论文需要的主张 |
| 自上次人审以来 EXPLORE 超过 GPU·时的 30% | 在追新现象，主线停滞 |
| 一句话主旨自上次人审以来改了 2 次以上，且没有变简单 | 叙事在加条件 |
| 新开测量轴而不收旧轴 | 不断加新的分析维度，没有一条走到 L2 |
| 运行没有实验卡 / 实验卡没有决策表 | 结果出来后才决定它意味着什么 |
| 主张的措辞超出验证范围 | 单系统机制被写成通用结论 |

处理：回到形态卡，问“哪 3 条主张撑起论文、各差哪一级证据”，把接下来的算力只排给它们。连续两个 lead 被平凡对照吸收时，执行 `README.md` §6 的“两次降级重置”。

---

## 9. 汇报与人审

- 每次会话结束：`logs/YYYY-MM-DD.md` 追加一条（做了什么 → 数字与 CI → 主张变化 → 下一步 → 需要人决定的事）。
- **人审在决策点触发，不按周**：D1–D6 交付；一个 pilot 跑完、要按决策表选分支；主张升到 L2 / L3 或被降级；出现漂移信号；开线 / 关线 / 转向 / 进入候选 / 投稿之前。人审前运行 `python3 tools/process/review.py <workbench> --write` 生成骨架（自上次人审以来的实验、主张变化、idea 状态、漂移信号）。
- 给人的汇报先说结论和数字，再说过程；负结果和作废结果与正结果同样汇报。
