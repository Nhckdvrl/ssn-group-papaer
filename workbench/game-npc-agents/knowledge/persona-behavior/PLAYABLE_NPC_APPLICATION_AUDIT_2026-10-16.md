# 可玩 NPC 应用审计：工业事实与现成强基线（2026-10-16）

本文件负责工业/引擎/基线部分，补充 I04/C06/P12 的应用判断。只读资料与已有代码，0 GPU/推理API/新实验，不修改研究状态；E77 按原队列完成。不把应用审计自动变成 E78/E79、训练方案或新平台。

## 1. 先给判断

**真实需求是玩家能用自然语言提出未写成菜单的合作办法，并在变化的游戏处境中得到可兑现、可修订的角色回应。** 快速说话、原子动作合法、简单任务优先可以由现成 LLM＋状态＋规则/可靠技能解决相当一部分；这些本身不足以解释为何还需要我们的研究。

E70–E77 揭示的推进与用途区别值得保留，但不能把已曝光 LIGHT 配置的 Get/Remove 困难泛称产业瓶颈。下一层应用问题应是：当玩家提出条件、等待 NPC 回答、实际履约或改变要求时，NPC 是否能理解双方在做什么、选择符合自身角色的方案，并把该方案落实到世界里；若普通强基线已解决，就承认其解决范围，追问剩下的真实交互而非继续调一句保护提示。

## 3. 工业强基线已经做到什么

论文 §4.2 已经构造**同一请求在可行/不可行状态中的配对监督**，改变库存、位置、阶段或可用动作；缺前提时允许澄清、拒绝或提出替代。Appendix C 的执行层支持可行性检查、临时动作注入、持续模式、优先级抢占和失败反馈；高层请求仍受生存反射约束。这是应继承的普通强基线，不能把“提供前提信息、先检查合法动作、做完一步后看反馈”申领为新方法。[作者正文及附录](https://arxiv.org/html/2609.29837)

这里的应用含义是我们的判断，不是作者已证明的普遍规律：

- **语言覆盖有限菜单外的表达与组合，执行仍受原生技能/权限约束。** 玩家可以笼统说“先别打，等我补给”，不必自己写BT节点；这与要求语言模型每帧自行瞄准是不同需求。
- **说话和动作需要共享真实完成状态。** 请求刚接受时能做、执行时被中断，NPC应重新解释或协商，而非持续说已完成。玩家据承诺采取下一步行动时，错误承诺会改变其可选方案。
- **普通分工可以先解决动作可靠性。** 角色对目标/受益者的取舍应由模型或明确政策选择，取物/移动/穿戴等可交可靠原生执行。这样仍有鲜明角色行为，不需要把每个动作前提都变成模型研究难题。

PUBG Ally 是共享团队命运的队友；它能证明真实玩家需要情境协作与恢复，**不能直接给“不完全共享目标 NPC 的私有利益冲突”背书**。本项目若要解释角色坚持、让步或条件合作，仍须在自己采用的原作者动机/状态上建立证据。也不把厂商“更像真人/更沉浸”的表述当我们已测到的收益。

## 4. 优先复用 LIGHT：具备真实行动后果的可玩候选

候选是已驻留的 [facebookresearch/LIGHT](https://github.com/facebookresearch/LIGHT)，本地pin `71a06cae8573048b1af41507ac52fe33b650fab3`，MIT。它并非只有问答数据：本次读 `PlayerProvider`、`TerminalPlayerProvider`、`PlayerSoul.handle_act/observe_event`、`World.parse_exec`、`BaseSoul` 记录和 `GraphEvent` 实现。玩家输入经原生事件执行，事件观察返给玩家/NPC；Give实际移动物品节点，摄取删除物品并应用原生health效果。角色说“给你了”不会自动执行Give。

现有源码入口：`light/world/player_provider.py`、`utils/terminal_player_provider.py`、`souls/player_soul.py`、`world.py`、`light/graph/events/graph_events.py`。本地README建议的 `scripts/examples/play_map.py` 在当前缓存不存在，不能宣称其命令本轮已启动；玩家 provider/引擎接口存在，已完成 E57/E64/E70–E77 的本地模型实体闭环，但这些不是新真人试玩。完整商业级UI恢复不是本轮任务。

**它容纳的自然玩家行动及玩法后果：** 以下为原生接口允许、可用现成角色/库存实现的交互类型，不是已运行的新实验；只选作者世界中实际支持的组合，不添物品或手写奖励。

| 玩家可尝试什么 | 脚本能解决到哪里；语言模块的用途 | 要观察的真实玩法后果 |
|---|---|---|
| 先询问角色为何需要某物，再提出“我给你现有X，换你手里的Y” | 固定商品/价格菜单适合脚本；玩家指向的物品、理由和条件不固定时，LLM能解释并映射到原生Give。交换依旧是两次真实转移，原引擎没有自动原子成交保证 | 双方是否真的得到承诺物、对话是否继续、自己物品是否仍可用于原作者目标；不以B拿到Y单独算成功 |
| NPC提出条件后，玩家接受、拒绝、提供现有替代或先履约 | 静态“一句请求后不再回复”的伙伴无法覆盖此分叉；无需新规划框架，先让合法回复/行动真正进入观察 | 等待是否被合理解除；NPC是否因实际履约改变选择；是否只口头接受却没执行 |
| 协商后改变要求，或角色行动后玩家再改变可见库存/位置 | 脚本可以保证合法性与取消动作；LLM处理自然语言变更和必要澄清。不能用玩家未被允许的远程删物/改私有状态制造失败 | 原方案是否仍可行，是否撤销过时承诺、提出原生可行替代；不能把改变需求后一律不履旧约叫失败 |
| 玩家允许NPC先吃/喝/穿戴，再谈其他可用资源 | 简洁任务规则及可靠动作宏可能已经完成；人物差可以体现在替代、等待与后续合作上 | 原生消耗/装备/转移及后续可行性；作者短中长期动机保留，原子goal不自动代表全部私人利益 |

这里的可用性问题不是“无限语言永远无法写脚本”的绝对断言，而是有开放表达/组合与动态状态时，简单脚本成本与角色选择怎样变化。若一项交互其实只有固定两分支，强脚本应当做对照，不能用弱脚本制造LLM必要性。

## 5. Action Castle 是有用对照，不再成为工程主线

已有 [ccb/agent-sandbox](https://github.com/ccb/agent-sandbox) pin `d7b872e396df2ef05ff8391de53e0563ca698cf3` 提供可玩文本冒险和网页入口。README明确默认是脚本NPC/关键词parser，LLM模式增加自然语言解析及动作选择，失败可Reflect并落回脚本。现有[E07](../../experiments/E07-native-actioncastle-closure.md)已去掉脚本fallback并完成6个本地episode；本轮未重跑/接云端。

本次定点重读 `action_castle.py` 的 Troll/Guard block与默认行为，以及网页/LLM模式README。喂鱼、饥饿解除、桥可通行是现成规则闭环；E07已证明“玩家Give鱼→引擎自动吃鱼/解除阻挡”，不能当NPC理解交换或人物目标的科学证据。它适合展示有/无脚本控制的权限与归因，也能提醒我们简单规则已解决多少玩法。

因此候选优先级是：**LIGHT现有作者世界的开放交互与真实物品后果，Action Castle作为强脚本/玩法闭环参照。** 不回到PCSP训练、校园漫游、Action Castle parser/bug长线，也不因缺少商业UI去新建平台。

## 6. 对照应当比“LLM有没有用”更强

后续应用验证若成立，至少要面对三个现成方案；这里不登记新实验矩阵：

1. **原生规则/脚本：** 能确定处理固定任务与已知条件，检查这段玩法是否原本已被覆盖。
2. **强本地LLM＋真实可见状态＋简洁规则：** 一句意图恢复、合法候选、明确反馈，角色/短中长期作者动机全链路一致。E63–E77已经表明这种普通支持不能忽略。
3. **上述决策＋可靠原生动作实现：** 给已选方案配原生可执行步骤，明确区分模型选择与脚本完成。若它解决了Get/Remove，剩余主张应聚焦角色在开放交互中的方案取舍与修订，而不是再调路径提示。

最终要辨认的是：玩家新增了哪种有意义的可选行动，角色怎样选择/回应，世界发生了什么，失败具体堵住哪段玩法。玩家信任、乐趣、沉浸不能仅由任务成功率或NPC台词替代，须另有实际玩家证据。既有自动化测量可以解释一部分形成过程，但不把其局部缺陷直接升级为“产业尚未解决”。

**本轮结论：** 可靠执行层与语言层结合已是可复用的强起点，研究应借它剥离机械执行负担。在这个基础上，继续研究自主角色怎样面对玩家条件、变化与请求，同时保留自身目标和有后果的选择，才有机会从现有“推进×用途”认识走向真正的可玩价值。先等E77完整结果，再结合玩家证据判断是否值得进入有限响应闭环，不机械追加编号。

**科学判断补充：** 应用审视不要求当前分析必须转成方法或立即开展玩家实验。“人物×目标取舍×行动前提”的整体证据若能解释原有矛盾、提出可检验预测，本身就有独立价值；普通执行支持或既有分层机制并不会抹去这份增量。下一次新增数据应更清楚地区分真实角色选择与原子执行负担，面对强普通baseline，并能说明相关变化如何映射到具体玩家可选行动及后果。哪些结论仍属于原生任务中的行为认识、哪些有真实应用证据，应随数据分别更新；不把所有现象贴成产业瓶颈，不据此增加自动去留bar、关闭研究线或改变状态。

## E77 完整结果后的独立判断

[E77设计](../../experiments/E77-dialogue-and-assigned-outcome-execution.md)、[Gemma完整结果](../../results/E77_gemma_complete.json)、[32B完整结果](../../results/E77_32b_complete.json)使整体解释更具体：**人物对真实行动的作用由互动中形成的立场、当前角色取舍和可行后果的实现共同形成；各项作用随目标类型改变。** 非Give31图固定C后，当前trait对Get8的平均差为Gemma+2.15pp[−5.38,9.68]、32B0[−4.30,3.76]；C来源差却分别为+16.13pp[4.84,28.49]、+10.75pp[0.54,21.51]，当前trait仍影响请求去向。这改写“Agreeable普遍直接提高执行能力/启动阈值”的解释，但并未证明差异严格为零或纯对话中介。

必须保留Give71反例：Gemma固定Agreeable来源对话时，当前trait仍提高Get8 +8.92pp[3.29,14.55]、原任务+9.86pp[4.69,15.49]，固定Firm来源对话时相应效应较小。不能再锁死“推进只由对话、分配只由当前人设”的二模块故事。明确指派原作者终局A在非Give的物理履约较高（Gemma F/A80.65/77.42%，32B96.77/93.55%），却在Gemma Give只有38.50/41.78%；指派请求者终局B的32B非Give履约仍有+12.90pp[5.38,21.51]人物差。明确终局是有效但不均匀的支架，不等于无损固定自然意图或识别潜在能力；既有C来源预测器表现更好也不是中介证明。

由此，最值得保留的是角色、互动立场、用途与前提的联合解释，而不是新增一个跨任务统一解码机制。下一批数据若进入应用，应回答具体玩家问题：**NPC提出条件后，玩家真实答复、履约或改变方案时，NPC能否据此修订选择并完成原生可行的行动，还是仍停在等待/相互矛盾的承诺中？** 先与LLM＋真实状态＋简洁规则/可靠原生执行比较，明确何者是合理角色坚持、何者是不理解互动、何者只是原子操作负担。无需用新提示网格给Gemma Give补分，不把请求者拿到物品当唯一成功；此判断不自动启动响应者实验、训练或新论文题目。
